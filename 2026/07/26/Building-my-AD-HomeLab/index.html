Overview :

This post is part one of a three-part series documenting the work I have done at my Summer Internship at COFICAB.

In this part, I walk through building my homelab, subject of all attacks, all the way from setting up the virtual machine to a fully configured Active Directory Domain Services setup, and then I attempt one simple attack as a test.

Disclaimer: This is a dummy setup created for a red teaming exercise. Nothing below reflects actual COFICAB systems, data, or infrastructure. I’m not permitted to test against real production environments. Any resemblance to real systems is purely coincidental.

Virtual Machine Setup

First things first, I’m choosing VirtualBox as my hypervisor: free, open-source and easy to use.
Then, I downloaded the Windows Server 2022 ISO file, an OS Microsoft built for admins to manage resources within an organisation. It leases a 180-day license, no key needed. This will be my Domain Controller target.

Network Isolation

This step is crucial for keeping the lab sandboxed. Given hardware constraints, I’m using my main Kali machine as the attacker host directly, rather than a separate Kali VM, so my goal is to isolate the Windows Server VM from my real network while still being reachable from Kali.

  1. To do this, we shut down the VM and go back to the VirtualBox Manager, and choose the network settings under File:

  2. Select the Host-only Networks tab then Create, VirtualBox will make one with a default subnet.

  3. Now we must attach the VM to it. Reminder to keep the VM powered-off throughout this entire process. Choose Network in the VM’s settings, then Attached to Host-only adapter under Adapter 1. Choose the name of the network (vboxnet0).

  1. Now we boot the VM in order to set a static IP within the network’s range. To do so, we open Network Status , then choose Change adapter options:

  2. Select Ethernet Properties, and choose Internet Protocol Version 4 (TCP/IPv4) .

Then fill in The IP address, Subnet mask and since this is becoming a domain controller, it’ll be its own DNS server, so it’s safe to set this now.

  1. Finally, we must enable ping through Windows Defender Firewall. I tripped over this and had to learn it the hard way: Windows Firewall blocks ICMP (ping) by default. We do this in Windows Defender Firewall with Advanced Security under Inbound Rules, and then we enable all the File and Printer Sharing (Echo Request - ICMPv4-In) rules.

The network link is successful and our VM is reachable from Kali.

Create Forest, Domain, DC

The AD hierarchy goes as follows :
Forests are the outer boundaries, and they define the shared schema and configuration partition for everything inside. Everything inside one forest trusts everything else inside it by default.
A Domain sits inside the forest. This is where actual objects live: user accounts, computers, OUs, group policies. My domain is coficab.lab .
Finally, a Domain Controller is the physical/virtual server that hosts a writable (or read-only) copy of that domain’s directory database (NTDS.dit) and runs the services (Kerberos KDC, LDAP, DNS) that make AD usable.

Since I’m working on a brand new server, the following Powershell command will create the entire hierarchy from scratch:

DSRM (Directory Services Restore Mode) password is a separate recovery-mode admin account used only if AD ever needs repair.

Note: The first DC is naturally where all 5 FSMO roles (schema master, domain naming master, PDC emulator, RID master, infrastructure master) land initially. These roles can be done by one DC at a time, so it’s the Admin’s concern to transfer these roles to other DCs eventually. But for the scope of my internship project, I won’t really have to do that. I can add it as a bonus later on, just to see how it works.

The server reboots automatically once this finishes, it comes back up as a live DC.

Kerberoasting : Manual attack attempt

Kerberoasting is a post-compromise Active Directory attack in which an authenticated domain user requests Kerberos service tickets (TGS tickets) for service accounts with registered Service Principal Names (SPNs), then attempts to crack those tickets offline to recover the service accounts’ passwords.

Here we use the GetUserSPNs.py tool, a Python script included with the Impacket Project that allowed us to enumerate SPNs, identify service accounts that are potentially Kerberoastable and request Kerberos TGS tickets and output them in a format compatible with password-cracking tools.
