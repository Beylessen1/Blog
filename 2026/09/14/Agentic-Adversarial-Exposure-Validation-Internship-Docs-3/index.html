Agentic Adversarial Exposure Validation (Internship Docs 3)

Author: Beylessen Jendoubi
Created: 2026-09-14
Updated: 2026-10-04

Overview :

This is part three of a three-part series documenting my summer internship at COFICAB. If you haven’t read parts one and two yet, the short version: part one built the lab and walked through the attacks by hand, part two built an LLM agent that reasons its way through the same attack chain autonomously.
But “domain compromised” is only interesting if you can measure it.
What makes an Adversarial Exposure Validation framework distinct from a glorified attack script is the second half of the pipeline: a deterministic scoring engine that reads Sysmon telemetry independently, maps events to ATT&CK technique IDs, and produces an honest answer to the question the agent can’t answer for itself : which of these attacks would your current detection stack have caught?
That’s what this post covers: the scorer, the results, and what the full system means as a piece of architecture.

Problem Statement

Many organizations, particularly outside large tech and finance sectors, rely primarily on periodic third-party penetration testing rather than continuous in-house red-teaming capability, leaving gaps between engagements during which new attack paths can emerge undetected.

This gap is the main reason Breach and Attack Simulation (BAS) tools exist. Instead of waiting for a human red team to show up once a year, a BAS platform continuously runs known attack techniques against your environment and tells you which ones your defenses caught. Companies like AttackIQ, Cymulate, and SafeBreach built entire product lines around this idea.

The problem is that existing BAS tools execute hardcoded playbooks. Every run follows the same fixed sequence of techniques, in the same order, regardless of what the environment actually looks like. That’s useful for compliance reporting because you can prove a control was tested, but it misses the point of what a real attacker does. A real attacker reads the room. They skip techniques that won’t work, pivot when something unexpected surfaces, and stop as soon as they have what they came for.

This project is an attempt to close that gap.

The Full System

Architecture

The AEV framework is two independent pipelines that share exactly one artifact: the run log.

The agent runs first. It initialises from a low-privilege credential, reasons over state, picks tools from its ATT&CK-mapped catalogue, and writes every step to a JSONL log : technique ID, tool called, status, duration, structured data payload. When it decides the goal is met, it stops. The log is its only output.

The scorer runs after. It reads the same JSONL log to know what the agent did and when. It reads Sysmon telemetry from the domain controller independently. It evaluates whether the events that should appear when a technique fires actually appeared in the telemetry window. Then it produces a report.

The key design principle in one sentence: the agent has no visibility into the scorer, and the scorer has no visibility into the agent’s reasoning : only its timing and technique sequence from the run log.

What the Agent Contributes

I covered the agent in detail in part two . For this post, three things are worth recalling:

  1. ReAct loop: the agent reasons over state, picks a tool, observes the result, repeats. It stops when it decides the goal is met.
  2. The LLM proposes, deterministic code decides: privilege checks, preconditions, and termination logic are never delegated to the model.
  3. The 5 vs 7 step gap: the agent skipped AS-REP Roasting (no vulnerable accounts in state after BloodHound) and called goal_achieved the moment the krbtgt hash landed. That adaptive sequencing is the thing a hardcoded runner can’t do, and it’s also what makes the detection surface smaller.

The run log is the agent’s output. It’s also the scorer’s input, which is why the JSONL format was designed from the start to be both human-readable during development and machine-parseable for the scorer.

Building the Scorer

The scorer is three Python modules. log_parser.py reads the agent’s JSONL run log and the Sysmon .evtx telemetry and normalises both into structured objects. detection_rules.py maps each ATT&CK technique to its expected event signature and checks whether it appears in the telemetry window. report_generator.py takes the results and produces a Markdown findings report and a JSON score summary.

Why it has to be independent

The agent knows it ran DCSync. It does not know whether the domain controller’s event log recorded it. Those are two different questions, and conflating them is the failure mode of every self-reported BAS tool.

Here’s a concrete example: Impacket’s secretsdump fires DS-Replication-Get-Changes-All on the domain object. That generates Security Event 4662 if the domain object has a SACL entry configured to audit replication rights. If it doesn’t, the replication completes silently. The agent gets the krbtgt hash. The security team sees nothing. A self-reporting system marks this as “detected.” The AEV scorer, reading the telemetry independently, calls it what it is: a critical detection gap.

The telemetry stack

Part one installed Sysmon with the SwiftOnSecurity config. For the scoring phase I switched to Olaf Hartong’s ATT&CK-annotated config : it’s noisier, but in a lab context where you want to catch everything rather than survive an alert flood, that’s the right trade.

The combination of Sysmon and default Windows Security logs covers the full attack chain. Sysmon Event ID 1 (process creation with full command line) catches BloodHound and Impacket by name. Security Events 4769 and 4768 are the primary signals for Kerberoasting and AS-REP Roasting. Security Event 4662 is what DCSync should generate , and in our case, didn’t.

Detection rules

Each rule is a function that takes the run record and the list of Sysmon events, checks for its specific signal, and returns a DetectionResult. One technique, one rule, one row in the report.

The Kerberoasting rule is the clearest to read:

RC4 (0x17) TGS requests to service accounts are anomalous by definition in any environment that enforces AES. If msDS-SupportedEncryptionTypes = 0x18 were set on the service accounts, this rule would never fire , and neither would the attack. The detection and the mitigation point to the same fix.

The scorer also produces a weighted total score: technique coverage (35%), step efficiency vs the golden run (25%), stop reason quality (20%), and Sysmon detection rate (20%). The score is a measurement instrument, not a report card, a low Sysmon score tells you your detection stack is quiet, but it doesn’t tell you whether that’s because the attacker was stealthy or because your logging is misconfigured. That ambiguity is intentional.

Results: Reference Run

The full technique findings table:

Technique Name Agent Executed Sysmon Detected Gap Priority
T1003.006 DCSync ✅ ❌ ⚠️ CRITICAL
T1558.003 Kerberoasting ✅ ✅ HIGH
T1558.004 AS-REP Roasting — ✅ HIGH
T1021.002 Lateral Movement (SMB / PtH) — ✅ HIGH
T1087.002 BloodHound Enumeration ✅ ✅ MEDIUM

The headline number is the DCSync gap. BloodHound and Kerberoasting were both detected , bulk TGS requests tripped the enumeration rule, and the two RC4 tickets for svc-sql and svc-backup showed up cleanly as Event ID 4769 with TicketEncryptionType=0x17. AS-REP Roasting wasn’t executed (no vulnerable accounts in state), and lateral movement wasn’t needed (domain was already compromised). That accounts for 50% coverage and perfect efficiency.

DCSync is the miss. The agent captured the krbtgt hash and called goal_achieved. The telemetry has no record of it. Security Event 4662 only fires if a SACL is configured on the domain object to audit that specific access right. Ours wasn’t. The detection rule is correct; the lab configuration was wrong.
It’s also, incidentally, the most common detection gap in real AD environments: 4662 auditing requires a deliberate, non-default step, so most environments simply don’t have it.

What the Results Mean

The 75.83% score is an honest number. The hardest technique to detect is the one that went undetected. A self-reported BAS system would have marked it as “tested.” The AEV scorer marks it as a CRITICAL detection gap.

The coverage score landing at 50% reflects the environment. The agent used three of the six tracked techniques. AS-REP Roasting was skipped because BloodHound found no vulnerable accounts; lateral movement was skipped because domain compromise was already achieved at step 5. A more complex lab would exercise more of the tree.

The more interesting number is the detection surface. A hardcoded runner would have fired AS-REP Roasting regardless, generating Event 4768 noise the blue team needs to account for. The agent didn’t, because it had no reason to.
This is interesting because not only it’s efficient, but the footprint also shrinked.

Limitations and What Comes Next

The lab is a single DC. There’s nowhere for lateral movement to go, so that branch of the agent is untested at any real depth. An intermediate workstation the agent needs to compromise before reaching the DC could change the result.

4662 auditing is the obvious first fix. The results surfaced it. Enable the SACL, re-run, confirm the DCSync event appears. That’s the most immediate validation the framework offers.

LangGraph for the next iteration. Building the ReAct loop from scratch was the right call for auditability and control. The tradeoff is no native checkpointing : a long run that crashes mid-Hashcat job has to restart from the beginning. LangGraph’s state graph maps naturally onto the existing AgentState; the security logic stays ours, the runtime gets more robust.

Final Reflection

The most interesting property of an agentic red teamer isn’t that the AI can execute attacks. It’s that its decisions are auditable in a way a human red teamer’s aren’t.
Regulators increasingly want evidence that controls were tested, not just assertions that they were. An audit trail that links each technique execution to the state that justified it is a different kind of evidence than a checkbox in a pentest report.

Now from an AI security point of view, I can’t help but wonder: What happens when the agent is prompted to be quiet about the attack ?

The current rules catch the noisy versions of every technique. The interesting research gap is not “can the agent compromise the domain,” it’s “can the agent do it quietly enough that the rules fail, and what does that reveal about the detection stack?”

Looking back at the whole project: reframing a blue-team monitoring brief into an offense-oriented BAS pipeline felt like the right call technically.

Finally, I’m thankful to my supervisor for sharing his expertise and his insightful guidance throughout this entire experience. I extend my gratitude to COFICAB Group as well, for making the internship experience both enriching and enjoyable.

This opportunity has allowed me to explore many axes and to push limits in ways I had not anticipated. From technical research to hands-on implementation, I was constantly bridging theory and practice and learning to operate effectively under real-world constraints.
