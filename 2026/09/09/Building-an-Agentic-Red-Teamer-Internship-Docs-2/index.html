Building an Agentic Red Teamer (Internship Docs #2)

Author: Beylessen Jendoubi
Created: 2026-09-09
Updated: 2026-10-04

Overview :

This post is part two of a three-part series documenting the work I have done at my Summer Internship at COFICAB.
In this part, I go through building an AI agent whose task is to red team the environment built in the first part of the series.

Agent’s Role

It’s paramount to understand the agent’s job and scope of execution before getting to more technical details regarding how it’s built.
The agent’s role is well-defined within this framework: given a low-privilege credential and a set of tools, it’s supposed to plan and chain attacks until domain compromise or no valid path forward exists.

ReAct : The Structure behind the agent

This is purely a system design choice.
But it wasn’t that hard to decide given the scope we already established : The ReAct framework is optimal as a conceptual backbone. The loop over Thinking, Action and Observation serves the goal we want to achieve and the pattern that needs to be followed in that order.

The following is a diagram explaining the logic behind the ReAct (Reason + Act) pattern.
The first input fed to the agent is the User Query, in our case it’s the credentials of the pwned low-privilege account. Then comes a phase of Reasoning over what we have and what can be done. Included within that phase is a regular assessment checking whether or not we’ve reached our goal. If successful, the loop ends and we’re provided our final answer. Otherwise, the agent decides the following Action, this generally implies tool-calling and execution of tasks. Based on the output of said actions, the agent enters a phase of Observation, during which it reflects on the outcome of the actions executed and updates the context, getting ready for the loop to restart again with more reasoning based on the new situation.

Here’s an example of one parse of that loop within my project’s context :

  • Thought: I have aymen:Password123 and no other credentials. The BloodHound enumeration tool will tell me which accounts are Kerberoastable.
  • Action: run_bloodhound(domain="coficab.lab", username="aymen", password="Password123")
  • Observation: {kerberoastable: ["svc-sql", "svc-backup"], admincount_users: ["svc-backup@coficab.lab"]}

Architecture : Three Layers

ReAct is an elegant design pattern, and to make the most out of its perks, I have built my agent around a three-layered framework:

1- State Machine : schema.py

This is my state’s representation. Here live state objects that would later be fed to the agent as stable context. Credentials, Privilege levels and more are defined and regularly updated as the chain of attack proceeds.

What makes it Special

The most valuable object in my script would be AgentState : a structured, queryable knowledge graph of creds, hosts and privilege levels that serves as a simple source of truth for the agent’s context.
Another important feature is preconditions : While the agent is given its liberty to reason and perform the action it judges the most suitable at each stage, it’s constrained by a set of conditions that have yet to be met before execution, otherwise the tool is out of use. These serve as a gate that mitigates the risk of of wrong steps or triggering a lockout.

2- LLM Interface : prompts.py

This layer is the boundary between the agent’s structured internal state and the model’s token space. Its job is translation: take the current AgentState and a catalogue of available tools, render them into a prompt the model can reason over, and parse whatever the model returns back into a structured tool call the outer loop can execute.

What makes it Special

The LLM builds the decision based on the following Reasoning Protocol:
ASSESS –> IDENTIFY –> JUSTIFY –> EXECUTE –> ANTICIPATE .
This is a plus for a couple of good reasons:

  • First, because it allows the log to be auditable and therefore bad reasoning is caught before it turns into a bad action.
  • Second, it forces a dynamic prioritization of the next tool based on the current states.
  • And finally, this well-defined system prompt imposing the role and scope of execution can significantly mitigate the chances of hallucination and tokens’ overconsumption.

3- Outer Loop : llm_agent.py

This is the executable layer : It owns the ReAct loop itself: initialise state, call the LLM interface, dispatch the chosen tool, feed the result back, repeat. It also handles logging, step counting, termination conditions and error recovery.
The termination logic is explicit: the loop ends when the model calls goal_achieved, when max_steps is reached, or when a hard error breaks the cycle.

What makes it Special

This is a thin layer by design and its only job is orchestration.
Starting from a tool call from the LLM interface, it finds the matching wrapper, executes it, writes the outcome to the run log, and hand the result back to the next prompt cycle.

Every step is written to a JSONL log before the loop continues. This is load-bearing: the run logs shown above are not incidental output, they’re the ground truth the scoring engine in part three will run against. Each entry carries the step number, the MITRE ATT&CK technique ID and name, the tool called, status, duration and a structured data payload.
The format was designed to be both human-readable during development and machine-parseable for the scorer.

Why Not LangChain ?

Tools like LangChain and LlamaIndex exist precisely for building LLM agent pipelines. However, for this use case, I deliberately chose to keep the core orchestration under my own control.

The first reason was auditability. AEV is a security-oriented system where every action needs to be explainable after the fact: what the agent decided to do, why it was allowed to do it, what tool was executed, what happened, and how the state changed afterwards.
Using a high-level agent abstraction would have meant delegating part of this control flow to the framework. Building the ReAct loop myself made the execution path explicit and allowed the run log to remain the authoritative source of truth.

The second reason was the tool contract. AEV’s tools are not generic functions exposed to an LLM. Each one represents a security-sensitive ATT&CK technique and therefore has a stricter execution contract: arguments must be validated before subprocess invocation, failures must be represented as structured ToolResult objects, and an individual tool failure must not bring down the outer agent loop. Keeping this logic in our own wrappers meant that the security policy remained independent from the LLM and from the orchestration layer.

Finally, I wanted a strict separation of responsibilities. The LLM should propose the next action, but it should not be the authority that decides whether that action is allowed, whether a privilege has actually been obtained, whether the attack goal has been reached, or whether the run should terminate. Those decisions belong to deterministic application logic.

This distinction is important in a security context. The architecture therefore follows a simple principle:

The LLM proposes. Deterministic code validates, executes, updates state, and decides when the run ends.

This approach also made the system easier to debug during development. When an attack chain failed, I could inspect the exact state, proposed action, validation decision, tool result, and resulting state transition rather than treating the agent as a single opaque component.

LLM Backend Decision

The agent needs a model that can reason over a structured state, pick the right tool from a catalogue, assemble valid arguments, and do this reliably across up to 20 consecutive steps without losing the thread.

While testing free models, I figured that bar was higher than it sounded. In fact, I have tried to run the attack chain with multiple free tier models and all of them turned out to be very limited.
Qwen2.5-7B-Instruct for example, successfully runs steps 1 to 3 but the output degrades afterwards and the model loses track of the context. It also loops over the AS-REP Roasting step, a valid real-life case but without any vulnerable accounts in our case.
The switch to DeepSeek V4 Flash solved it.
DeepSeek V4 Flash is fast, cheap at scale, and maintained reasoning quality across the full chain. The golden reference run (7cff605d) completed in 5 clean steps with no mid-chain degradation.

The 5 vs 7 step difference between the hardcoded runner and the LLM agent is worth noting: the agent skipped AS-REP Roasting (no vulnerable accounts in state after BloodHound, so correctly deprioritised) and never reached lateral movement (it called goal_achieved once the krbtgt hash was captured : domain compromise already achieved).

5-Step Chain

The attack chain the agent is expected to reason through follows a straightforward decision tree.

Everything starts with BloodHound: a full AD enumeration that maps the domain, identifies Kerberoastable accounts, flags pre-auth disabled users, and surfaces privilege levels.
From there, two roasting techniques run in parallel depending on what BloodHound found: Kerberoasting for accounts with SPNs, AS-REP Roasting for accounts with pre-authentication disabled. Both feed their hashes into Hashcat for offline cracking.

After cracking, the chain hits its only decision point: a privilege check on the recovered credentials. If any cracked account carries Domain Admin rights, the path goes right, straight to DCSync, extracting the krbtgt hash and ending with Domain Owned. If none of the cracked credentials are DA, the chain goes left, Lateral Movement to reach a higher-privilege host, followed by Secrets Dump to harvest further credentials, looping back to Hashcat with whatever new material surfaces.

The hardcoded runner follows this exact tree in fixed order. The LLM agent’s job is to arrive at the same decisions by reasoning over state.

Preparation : Tool Wrappers & Hardcoded Runner

Before the LLM agent could run a single step, every technique in the chain needed a reliable, deterministic wrapper. The tool library covers eight ATT&CK-mapped techniques: BloodHound enumeration, Kerberoasting, AS-REP Roasting, hashcat cracking, DCSync, SAM/LSA credential dumping, lateral movement , and a goal_achieved terminal call. Each wrapper enforces a strict contract: validate arguments before touching the network, return a structured ToolResult regardless of failure mode, never raise an exception the outer loop can’t catch.

The hardcoded runner was built first, before any LLM was involved. The idea was to write a script that executes the full attack chain in fixed order, validate every tool end-to-end against the live lab, and treat the result as ground truth.

Future Work : LangGraph

Building the orchestration layer from scratch gave me a much better understanding of what an agent runtime actually needs to handle. It also made the limitations of a custom implementation increasingly obvious.
The natural next step would therefore be to evaluate LangGraph as the orchestration layer for AEV.

Unlike a high-level agent abstraction, LangGraph exposes the workflow as an explicit graph of state, nodes and transitions. This maps well to the architecture already implemented in AEV.
The current AgentState could become the graph’s state. The validation logic could become a dedicated policy node. Tool execution could live in its own node, followed by a deterministic state-update node. Conditional edges could then handle decisions such as:
-Have we reached Domain Admin?
-Is DCSync now allowed?
-Are there new credentials to crack?
-Is lateral movement required?
-Has the attack reached its terminal condition?

In other words, LangGraph would not replace the security logic already built into AEV. It would provide a more mature orchestration runtime around it.

The biggest advantage would be durability. The current implementation keeps the active state in memory and writes the run to JSONL for auditing. This is sufficient for a controlled lab run, but it does not provide native checkpointing and resume capabilities. A long-running attack chain should not have to restart from the beginning because the process crashed halfway through a Hashcat job.
LangGraph’s checkpointing model would allow the state of a run to be persisted between steps and resumed from the last valid checkpoint. This becomes particularly relevant as the number of steps and long-running operations increases.
The graph structure would also make more complex workflows easier to express. Parallel branches, conditional paths, retries and reusable subgraphs could be represented directly rather than growing the custom outer loop with more control-flow logic.

The goal would therefore not be to replace the architecture developed in this project, but to evolve it:
AEV’s security logic remains ours. LangGraph becomes the runtime that orchestrates it.

Reflections

The hardest part of this project by far was making the model’s reasoning legible enough to trust. Every architectural decision in this project traces back to that constraint: the audit trail isn’t a nice-to-have feature, it’s the thing that makes the whole system defensible. Once I committed to the principle that the LLM proposes and deterministic code decides, the three layers followed naturally.

However, the agent is only half the system. The real question is not “did the agent succeed?”, but “did the domain’s defenses detect it?”.
That’s what the log scorer is for, and that’s what the next post is about.
